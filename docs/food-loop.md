# The food loop: rules → meals → requirements → pantry → list → shopping → pantry → cooking

This pass makes the shopping → pantry → cooking loop reliable. The two beta
failures it fixes:

1. The planner recommended regular milk to someone who prefers lactose-free milk.
2. Rice was in the pantry, yet the grocery list said "buy rice" with no explanation.

Both came from the same gaps: dietary preferences were loose strings the AI was
asked to "respect", and pantry coverage was a boolean on a name match. Both are
now deterministic code paths that every planner shares.

## Pipeline

```
USER FOOD RULES ─┐
                 ▼
PLANNED MEALS ─► NORMALIZED REQUIREMENTS ─► PANTRY AVAILABILITY ─► QUANTITY DIFFERENCE ─► SHOPPING LIST
  (AI or template,    (family / variant,       (compatible variants,     (required − on hand,     (BUY / PARTIAL /
   rules applied)      servings, "used in")     known qty / A lot /       in servings → purchase   ALREADY HAVE /
                                                Some, overrides)          units)                   CHECK YOUR PANTRY)
```

| Stage | Where | What it guarantees |
| --- | --- | --- |
| Food rules | `src/food/rules.ts` | `deriveRules(prefs)` turns the legacy `dietPrefs` / `dislikes` / `likes` **and** the new structured `foodRules` into one model: `hard` (allergy, intolerance, religious, diet), `avoid` (avoid / prefer-substitute with an optional substitute), `prefer`, `dislikes`, `likes`. `resolveIngredientForUser(ingredient, rules)` is deterministic: `ok`, `substituted` (with a macro delta when known), or `forbidden`. `validateMeal` repairs or rejects any generated meal. |
| Ingredient model | `src/food/families.ts` | Families (milk, rice, bread, …) with variants and tags (dairy, lactose, gluten, pork, shellfish, …). `pantryCovers(requirement, pantryItem)`: any variant of the family covers the requirement **unless** the pantry variant carries a tag the requirement lacks. Jasmine rice covers rice. Regular milk never covers lactose-free milk. Unit conversion for the common cases (lb/oz/g/kg, cup/tbsp/tsp/ml/L, each/dozen, purchase units like "bag" or "half gallon"). |
| Requirements + coverage | `src/food/reconcile.ts` | `requirementsFromMeals` sums servings per normalized ingredient (quantities like "2 cups rice" are converted; plain names count as one serving; a double batch doubles). `coverRequirement` returns `required / onHand / toBuy` and a status: `full`, `partial`, `none`, or `confirm` (the pantry only says "Some", or "A lot" against unusually high demand). Every row carries a `why`. |
| Reconciliation engine | `src/services/foodWeek.ts` → `reconcileShoppingList(weekId)` | Separate from meal generation. Runs after a plan is generated or replanned, and again whenever the pantry changes (`onPantryChanged`). Rewrites only derived, un-purchased rows; purchased rows, hand-added rows and overrides ("I already have this", "Buy anyway") survive. Meals are never regenerated by a pantry change. |
| Shopping → pantry | `finishShopping` | Purchased rows only, with the actual quantity, stored under the canonical variant and merged into an existing row. Skipped rows never reach the pantry. |
| Cooking → pantry | `consumeForRecipe` | Requirement × servings, from compatible variants, soonest-expiring first. Staples never tick down. Logging a cooked recipe consumes automatically. |

## Rule semantics

| Kind | Meaning | Planner behaviour |
| --- | --- | --- |
| `allergy`, `intolerance`, `religious` (and diet chips: vegetarian, vegan, dairy-free, gluten-free, halal/kosher, nut-free) | HARD RESTRICTION | Never generated. A substitute is used only when it is explicit or the family is swappable (milk → oat milk for dairy-free; a beef dish is excluded, not quietly made plant-based). Meals that cannot be repaired are rejected. |
| `avoid` | Don't use it | Substitute when one is known, otherwise excluded. |
| `prefer-substitute` | Not forbidden, but use the substitute | Substituted everywhere; kept only when no substitute exists. |
| `prefer` / `likes` | Rank up | Scoring only. |
| `dislike` | Rank down / exclude recipe | Never a prohibition on an ingredient by itself. |

The milk example: "avoid regular milk, prefer lactose-free milk" is a
`prefer-substitute` rule targeting the `milk` variant. Dairy stays allowed, a
protein shake becomes protein powder + lactose-free milk, and `lactose-free
milk` is what the list asks for ("swapped in for milk by your food rules").

## Where the one rules engine is applied

- Template week (`planner/weekTemplates.ts`): recipe exclusion, substitution before selection, the snack library (`snacksFor`).
- Template day (`planner/mealTemplates.ts`) and quick adds (`quickAddsFor`).
- Pantry suggestions (`planner/pantrySuggest.ts`) and day adjustments (`planner/dayAdjust.ts`).
- AI outputs (`ai/generate.ts`): the prompt gets the structured rules (`ctx.nutrition.foodRules`: hard restrictions, intolerances, substitutions, preferences), and every returned meal still goes through normalize → substitute → validate. Repaired meals are kept with adjusted macros (labelled as estimates when the substitute's nutrition is unknown); rejected meals are replaced from the template library, and a day plan that loses a main meal falls back to the template entirely.
- Settings changes and "Don't recommend this" call `applyRulesToWeek`, which repairs the pending planned meals in place and reconciles the list.

## Unknown quantities

| Pantry says | Coverage |
| --- | --- |
| known quantity | converted to servings; `full` / `partial` by the difference |
| A lot | adequate (`full`) unless the plan needs more than `max(8, 1.5 × servings per purchase unit)`; then `confirm` |
| Some | `confirm`: "Rice is marked Some. Need ~4 servings. Enough?" → **Yes** sets the pantry to cover the plan, **Low** keeps a small amount and buys the rest, **Out** buys it all |
| None / 0 | `none` |

## Pantry

- Names are stored as the exact variant when known (`lactose-free milk`, `jasmine rice`), with `family` / `variant` / optional `product`.
- Duplicate prevention: adding "rice" when "jasmine rice" exists, or "egg" when "eggs" exists, asks **Update quantity / Add separately** instead of creating a second row.
- Planning is pantry-first: on-hand ingredients score up, expiring (within 4 days) and opened perishables score higher, and the AI is told to plan around them.
- `wasteScore` is a lightweight optional signal (expired unused, bought-but-unused).

## Backward compatibility

Existing `dietPrefs`, `likes` and `dislikes` keep working unchanged; they are
derived into the same rule model. `foodRules` defaults to `[]`. The grocery
item boolean `coveredByPantry` is still written (true only for `full` coverage)
so older rows and screens read correctly; the new columns
(`required_servings`, `on_hand_servings`, `coverage`, `canonical`,
`substituted_from`, `used_in_counts`) and pantry columns (`family`, `variant`,
`product`) are added by migration `0004_foodloop.sql`.
